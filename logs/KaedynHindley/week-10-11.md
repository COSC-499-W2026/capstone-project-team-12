### For PR #323 (User Logout):
As part of requirement A22, the user needs to log out of the app: they press log out, the app calls `POST /api/v1/auth/logout` with the refresh cookie it holds, and the app discards its access token. After that, this device cannot get new access tokens without signing in again.

Therefore, I implemented code so that every signed-in user (students, staff and admins) can log out of the device they are using. Logging out revokes the refresh token family of that sign-in and clears the refresh cookie. The user's other devices stay signed in.

When I reviewed the first version of the `logout` route in `api/v1/auth.py` and `logout_user` in `accounts/logout.py`, Eddy noticed that the route found the user from the access token and revoked all of the user's refresh tokens. This was a problem for three reasons: logging out failed with 401 once the access token had expired (after at most 60 minutes), a disabled account got 403 and could not log out, and logging out on one device signed the user out on every device. Therefore, I changed the route to find the sign-in from the refresh cookie instead, and replaced `logout_user` with `logout_session`, which only revokes the token family that the cookie belongs to. The route now always returns 204, so a client can always finish logging out.

When Eddy reviewed the cookie handling in the route, he noticed that the first version did not clear the refresh cookie at all, and my first fix called `response.delete_cookie("refresh_token")` without the cookie's path. The cookie is set with the path `/api/v1/auth`, and a browser only deletes a cookie when the delete matches the cookie it holds, so the cookie was never actually removed. The test only checked the text of the `Set-Cookie` header, so it passed anyway. Therefore, I added `_refresh_cookie_options()`, which setting and deleting the cookie both use, and changed the test to check that the client's cookie jar really drops the cookie.

This data `refresh_token` may be vulnerable to being stolen and reused after the user logs out (session hijacking). Therefore, it uses a security-based sanitization by never storing or looking up the raw token: `logout_session` hashes it with SHA-256 and only matches the hash. It revokes every token in the sign-in's family, not only the one sent, so no token from that sign-in can be refreshed afterwards. The cookie stays `HttpOnly`, `SameSite=Strict` and limited to the `/api/v1/auth` path, and it is deleted with the same options it was set with.

This data `refresh_token` may be vulnerable to revealing account information, such as whether a token is still valid or which account it belongs to. Therefore, it uses a privacy-based sanitization by returning the same empty 204 response in every case: a valid, revoked, unknown or missing token all look the same to the caller, and the response contains no user data.

The PR does not contain any temporary workaround because logout uses the existing refresh token families and `revoke_token_family`, and the cookie settings come from the app config. There are no placeholder values or stubbed calls.

The PR only contains small functions that total to 254 lines of code.

I moved the cookie settings into `_refresh_cookie_options()` so setting and deleting the cookie do not repeat them, reused `revoke_token_family` instead of writing a new revoke query, removed the imports left unused when the route stopped using the access token (`get_current_user`, `User`), used early returns in `logout_session` so it has no nested conditions, and ran `ruff format` and `ruff check` to ensure that my feature contribution does not contain any of the following:
- hardcoded values
- duplicate code
- dead code
- unnecessary function calls
- excessive conditional logic
- deep nesting
- high cyclomatic complexity

The functionality works correctly because the happy path tests involving `test_logout_revokes_tokens`, `test_logout_clears_refresh_cookie`, `test_logout_keeps_other_sign_in_working`, `test_logout_keeps_other_users_signed_in` and `test_login_works_after_logout` passed.

I wrote tests to cover abnormal situations involving `test_logout_with_expired_access_token_revokes_session`, `test_disabled_account_can_logout`, `test_repeated_logout_keeps_revoked_at` (logging out twice keeps the first revoke time), `test_logout_without_refresh_cookie_returns_204`, `test_logout_with_unknown_refresh_token_returns_204` and `test_logout_session_does_not_commit`, and they passed.

### For PR #324 (GET /me/profile):
As part of requirement A24, the user needs to view their account information: they open their profile, the app calls `GET /api/v1/me/profile` with their access token, and the app shows their username, email, role, active classes, current class and practice language.

Therefore, I implemented code so that every signed-in user (students, staff and admins) can read their own profile. Students get the classes they are actively enrolled in, newest first. Staff and admins get an empty class list. I also added `email` and `classes` to `ProfileResponse`, so `PATCH /me/profile` now returns the same fields as the new GET route.

When I reviewed the first version of `_profile` in `api/v1/me.py`, I noticed that it queried the `ClassEnrollment` table directly. This was a problem because it listed every enrolment, including classes the student had left, been removed from, or that were archived. It also copied the results into a list one by one with a loop, so each item was a database row instead of a class ID, and it made the route layer read the engagement component's table instead of going through engagement's interface. Therefore, I replaced the query with `get_active_class_ids` from `engagement/interface.py`, which only returns active enrolments, and made `classes` a required, documented field instead of an optional one that defaulted to `None`.

When Eddy reviewed `_profile`, he noticed that it read the active classes twice: once for `classes`, and again inside `current_class_id`. This was an extra query, and if a class ended between the two reads, `current_class_id` could name a class that was not in `classes`. Therefore, I added an optional `active` parameter to `current_class_id`, so `_profile` reads the list once and passes it in.

When Eddy reviewed the route's documentation, he noticed that it did not say that admins can read their profile but `PATCH /me/profile` refuses them with 403 FORBIDDEN_ROLE, or that a class a student left and rejoined keeps its first join date. Therefore, I documented both in the API descriptions and added `test_profile_keeps_the_first_join_date_of_a_rejoined_class`.

This data `ProfileResponse` uses the input validation to ensure it adheres to the API schema: `id` and every entry in `classes` must be UUIDs, `role` must be a `UserRole`, and `preferred_language` must be a `Language` or null. The route takes no request body or parameters. Its only input is the access token, which `get_current_user` checks (signature, expiry and an active account) before the route runs.

This data (the user's profile) may be vulnerable to broken access control, where one user reads another user's profile by changing an ID in the request (IDOR). Therefore, it uses a security-based sanitization by not taking a user ID at all: the route only returns the profile of the user named in the verified access token. A missing or invalid token is refused with 401 NOT_AUTHENTICATED.

This data `email` may be vulnerable to exposing personal information. Therefore, it uses a privacy-based sanitization by returning it only to the signed-in owner of the account, and `response_model=ProfileResponse` only lets the listed fields through, so other `User` columns, such as the password hash, are never sent.

The system uses a layered, component-based design (routes in `api/v1/`, logic in the accounts and engagement components, which other components use through their `interface.py`) because enrolments belong to the engagement component while the profile belongs to accounts. Benefits for using this pattern include:
- The profile route does not depend on engagement's tables. If enrolments are stored differently later, only engagement changes.
- GET and PATCH both build their response with `_profile`, so the two routes always return the same shape.

The PR does not contain any temporary workaround because the classes come from real enrolments through the engagement interface, and GET reuses the same `_profile` builder as PATCH. There is no placeholder data and nothing that needs to be replaced later.
